# Extraction failure investigation — 5 November 2026

## Root cause and evidence

The existing ignored `benchmark-live.json` records one `stale-python` case, latency **2405.22 ms**, one logical model call, zero searches, zero reported Tavily credits, no claims, status `incomplete`, and warning **`Upstream HTTP 429`**. That warning was generated by the HTTP error handler before a model response could be parsed. The evidence establishes a throttled upstream request, not invalid JSON, an empty model response or a genuine empty extraction. The saved record cannot distinguish a Bifrost gateway limit from Gemini quota/rate limiting; no raw upstream error body was retained.

The classification defect had two parts: the engine collapsed service errors into a warning plus an empty claim list, and the benchmark treated every unmatched expected claim as `missing`, regardless of whether extraction executed successfully. Its 0 extraction recall and detector failure counts therefore mixed service availability with detector quality.

No live model or Tavily requests were made during this investigation. The original benchmark file and credentials were preserved. `work/extraction-failure-analysis.json` is a separate offline reclassification of the saved observation, not a new live result.

## Corrected behavior

- `ServiceError` carries a safe code, optional HTTP status and stage diagnostics. Responses/headers, credentials and upstream bodies are never stored in the error object returned to users.
- HTTP 429 becomes report status `upstream_error`, `extraction.status=failed`, and an error with stage `extraction`, code `http_error`, HTTP status `429`. Empty content/choices/HTTP bodies, invalid JSON, truncation, malformed envelopes and invalid extraction schemas have distinct codes and report `unavailable`.
- The whole extraction is validated before any search, preventing a malformed later claim from causing partial paid work.
- A valid `{"claims":[]}` is still a successful extraction response. If a known factual benchmark claim is omitted, it is a genuine `missing` claim and counts against extraction recall.
- Search/judge service failures are separately staged. Successful extraction can still be measured when a later service fails, while that claim's detector verdict is unavailable for quality scoring.
- A deliberate search-budget skip is `not_evaluated`, rather than a detector error or an uncertain evidence verdict. Zero-search timeless claims still score normally.
- Accuracy, extraction recall/precision, stale recall and coverage are `null` when no relevant case is evaluable. Counts/denominators, availability and end-to-end success remain visible; this does not hide failed requests. Costs and latency include failed cases. Missing model billing metadata is explicitly incomplete, not assumed free.
- Overload stopping uses typed status metadata, with exact-message compatibility for old reports. A harmless “429” in model reasoning no longer triggers a stop. Partial output includes `run_status=stopped_upstream_error` and requested versus attempted case counts.

For the saved failure: **1 upstream extraction failure, 0 evaluable cases/claims, 0 genuine extraction misses, null quality metrics, 0% extraction/pipeline availability, 0% end-to-end success**. Original 2405.22 ms, one model call and zero search counters remain unchanged.

## Gemini compatibility review

The request still uses the existing model, JSON object format, non-streaming output, minimal reasoning and a 2,800-token output cap. No credentials, model identifiers or gateway settings were changed.

Google documents [structured output and a 65,536-token output limit for Gemini 3 Flash Preview](https://ai.google.dev/gemini-api/docs/models/gemini-3-flash-preview?hl=en), and [minimal thinking support](https://ai.google.dev/gemini-api/docs/thinking?hl=en). In the pinned Bifrost source, `core/providers/gemini/utils.go` maps `json_object` to `application/json` without a schema; `gemini_test.go::TestThinkingLevelFromEffort` covers minimal effort for this model. This is compatible in principle with the extraction prompt. JSON mode does not enforce our claim schema, and a bounded output limit can still truncate a long/thinking-heavy response. Such failures now have explicit diagnostics.

This saved request received HTTP 429 before response parsing. Raising token limits or weakening the prompt/citation rules would not diagnose that refusal. The running gateway's actual handling of these parameters remains unverified under the current quota; no live compatibility probe was made.
